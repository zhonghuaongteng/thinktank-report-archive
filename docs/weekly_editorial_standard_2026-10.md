# 周报写作与漏项核验规则（2026-10-05）

## 2026-11-22 专题从取材到成稿

**重点单篇默认写成详读。** 以11月22日专题详读版作为取材深度的参考。在已经讲通的主线上，继续找一个读者会追问的环节，回到原报告的案例、图表、访谈、方法或制度条款，把“具体如何发生、又凭什么如此判断”再往下讲一层。有直接关系时，可引入当事方公告、公开评估或原始数据与主材料对照，交代时间和归属。例如，企业融资可追到谁领投、整轮资金用在哪。调查数字可追到谁受邀、谁实际回答。资料进入正文的位置由它能解释的问题决定，避免堆案例或反复陈述同一判断。刊前通读时，检验新增段落是否让读者多理解了一个关键环节。原有取材记录和复述继续使用，篇幅按证据决定。

选定重点时先从陌生读者的疑问出发。例如，看到“核心大学群”，读者首先需要知道为什么提出这项制度、哪几方要共同做什么；看到“EIC基金企业”，需要知道谁在出资、企业为什么寻求这种支持。抓取的新闻标题和摘要是回到原文的线索。同期发布日决定收录资格。为解释来由可以追溯原文所引的早期方案、制度主页或上次会议，注明它们是背景。

1. **取材时找出断点。** 核读完整报告或会议主件，随手记下能回答读者疑问的原文链接、页码或小节，以及那里实际说了什么。分清问题从何而来、参与者怎样行动、证据怎样支持作者的判断。遇到“遴选”“改革”“影响”这类词就追问一次具体对象和过程。原文没说清的关键环节，沿官方引用补找。材料确实只够交代一条消息时转作简讯，重新从本期合格候选中选重点。
2. **先写正文，再提炼摘要和漫画。** 为读者写一篇可以单独读懂的文章。提案要交代既有做法为什么遇到困难、谁负责哪件事，以及哪些安排仍待决定。调查先解释被调查的服务和企业怎样经历它，再把各题的回答者、比较基准及自报性质放在数字旁。争论可从触发争论的决定写起，把一方的理由交给另一方回应。按具体材料取舍，一段接住上一段留下的问题。需要时充分展开，篇幅由实质信息决定，避免用通用意义或拆分小标题填空。
3. **从成稿反向检查。** 编辑放下原文，通读实际正文，写一小段连贯复述，说明事件或问题、最能解释它的行动或依据，以及目前知道了什么。凡是复述时还要从脑中补背景、猜承接关系，或依赖漫画才懂的地方，回到原文补读、改稿，再复核。复述和取材笔记留内部，读者端照文章本身的逻辑组织。标题、导语或正文改动后，重新通读。
4. **防止排版退回摘要。** 用同一份核准正文生成手机、PC和公众号，各篇按原文URL对应。独立检查两种阅读版的段落顺序和末段，以及PDF分页、公众号本地排版成品。记录每篇原文摘记、编辑复述、核准稿指纹。核验工具只检查这些记录和文本传递，文章是否讲通由实际通读判断。

同一期的重点复核保存为 `docs/run_receipts/<D>_feature_reading.json`。对象含 `features` 列表，各篇含 `url`、`source_notes`（每条为 `url`、`locator`、`finding`）、`retelling` 和 `reviewed_sha256`。先从核读原文写摘记，再在通读定稿后写复述，最后用仓库 `scripts/check_weekly_feature_reading.py` 的 `fingerprint(item)` 记录当时标题、导语和正文的指纹。用当期完整入选文件和实际排版成品运行以下检查，正文改动后不要仅刷新指纹。

```text
python scripts/check_weekly_feature_reading.py --items <当期items.json> --review <当期feature_reading.json> --pc <PC漫画HTML> --mobile <手机HTML> --output <当期feature_reading_check.json>
```

正式投递前修正漏项、过期复核或成品缺段。独立运行原有选材与数量检查，简讯继续按自身信息量处理。已交付期另存修订阅读版。

## 2026-11-16 用户修订：讲透报告，突出证据，分别制作两种阅读版（优先执行）

读者版的主要篇幅用于阐述报告观点、事件前因后果和关键证据。正文、摘要、首页、简讯、图注和漫画均不出现防御性的表述、编选边界说明或例行免责声明。核读范围、获取过程、来源完整度、编选理由、版权处理、事实复核和编辑自证留在内部编选记录及回执，不占读者篇幅。

- 先讲清这份报告为什么此时提出这个问题：原来发生了什么，谁遇到怎样的现实困扰，近期出现了什么变化，报告最想表达的判断是什么。读者不点原文，也能理解事情的来龙去脉；开头不能只给抽象结论。
- 围绕报告自己的论证展开事件、观点和证据，不套固定主题或栏目。主要篇幅说明作者为何这样判断、哪些参与者采取了什么行动、哪些安排产生了怎样的变化。背景和过程按理解需要交代，不能压成漫画标题的扩写。
- 主动提取最有辨识度的证据亮点：关键对照、反常结果、具体案例、制度细节、图表或能改变判断的数字。把它们放到导读或相关主论点附近，解释“这条证据支持了什么、为什么值得关注”，不能埋在长段末尾、小字脚注或内部记录里；不按数量凑亮点。
- 用具体事实自然表达研究对象、时期、统计口径和实施状态。例如写“报告建议由X资助，让Y先在Z开展试点”，无需再加“只是方案、并非已证实成效”。写清作者与行动即可，不另设“边界、局限、如何理解本报告”或“不能据此推断”等防御段落。
- 删去“原文未提供所以不能……”“本文仅作……”“不代表……”“不应将其理解为……”等编辑自我辩护。对原报告自身的重要分歧与争议，应直接解释不同主张和各自证据，不能把争议替换成免责声明。事实准确性通过措辞、主语和证据实现。
- 简讯同样交代最必要的来由、具体变化和主要发现；篇幅可以随信息需要增加，不能为了短而只剩口号或术语串。
- 逐篇验收时，应能直接从读者稿中回答：事情为何发生、报告主张什么、最值得记住的证据是什么。任一项说不清就继续改写；字符数、材料计数和格式通过不能代替这个判断。上述问题是编辑检查，不是读者端固定栏目。

### 漫画要讲事情，手机版与PC漫画版分别设计

- 每周提供“手机版”和“漫画版（PC）”，基于同一份已经核准的完整正文与简讯制作；两版都保留完整可选取文字，不以图片替代正文。原有桌面稿作为PC漫画版，不再把手机图原样放大充当PC图。
- 手机漫画采用少字大字、纵向阅读和明确的行动过程。PC漫画独立编写分镜和提示词，可以用更丰富的人物互动、事件顺序、对照场景、流程及图表，把现实困扰、参与者行动、关键证据和报告主张讲连贯；分镜多少服从报告内容，不固定为四格或单一场景。
- 漫画中的人必须在做具体的事，物件、对话和箭头要解释谁与谁、前后发生什么、做法为什么有作用。不能只画“明确需求—加强合作—实地验证”等抽象标签，不能把口号提炼当作完成。
- 优先把原文的案例、对比、数据和制度过程画出来。原文没有的事件和成效不编造；一般性人物形象可以示意参与角色，人物台词用于通俗解释原文观点，不能冒充真实引语。
- PC与手机的图片、分镜、提示词和验收记录分别保存。换尺寸、裁切、放大、重新压缩或仅多加标签，不算完成PC独立设计。先核准正文，再写两套分镜，再生成、逐幅对照原文、分别检查实际PDF和HTML。
- 每周在同一封原授权邮件中同时发送两版PDF与HTML，共四个附件；继续原收件人、原主题与每期一次发送，分别核对文件名、实际页数、哈希和已发送附件。历史已投递周次不因本规则自动重做或重发。

## 2026-10-18用户修订：说人话，讲清实际工作（优先执行）

用户反馈“英国工程生物学枢纽把共享技术与应用任务分开组织”令人感兴趣，但正文过于抽象、看不懂。此要求适用于以后各期的首页、标题、摘要、重点正文、简讯和漫画。

- 先让读者知道具体问题：谁遇到了什么困难，谁准备做什么，具体怎样做。按材料本身展开，不机械套固定栏目。
- “共享能力、节点治理、应用任务、机制衔接、赋能、生态”等词不能充当解释。确须保留术语时，紧接着用普通话讲明实际行动，例如“改进预测和自动测试的方法，供不同研究团队使用”。
- 讲组织模式时，把人、钱、工作和决定联系起来：参与者分别做什么，共用什么，谁出钱、谁决定、谁检查；原文未说明的地方不补造。不能只把这些项目列成抽象名词。
- 优先使用原文的具体例子；原文采用假设情景时，直接说明其设定，再解释情景中的行动与结果，不新增虚构案例来替代原文证据。
- 漫画以人物行动、具体物件和清楚的前后关系解释主问题；不把抽象术语搬进方框。读者不看正文也应能说出图在讲什么。图不能取代正文的完整说明。
- 交付前逐篇做一次普通读者检查：读完开头能否复述问题和主要做法？每个抽象判断后是否有可理解的动作或证据？若仍需另写一段口头解释才能读懂，应先把解释写进周报，再渲染。
- 已发送周报的编辑修订另存阅读版，保留原附件；未经新的明确发送授权，不自动重发。

### 简讯同样说人话

- 简讯篇幅短，也要让读者看懂谁遇到什么问题、发生了什么具体变化、有关方面准备怎样做或研究发现了什么；按原文的信息选择重点，不机械塞进固定句式。
- 用具体主语和动作写出新增信息，不能把长文压成“协同、赋能、治理、生态、能力”等名词串。专业术语和缩写首次出现时用一句短解释说明实际含义；解释不下时可以多写一句，不能以简短为由省掉理解所需内容。
- 保留发布机构、日期、必要数字的口径及来源链接；准确区分征求意见、计划预告、项目获批、已经实施与已有结果。通俗改写不得扩大原文结论。
- 每则简讯单独做普通读者检查：不点击原文，能否说出这条消息具体讲了什么、哪里有变化？只剩题名、口号或抽象判断时，先改写再排版。

重点解读与简讯分层安排。值得深入展开、原文充实的材料写重点；有清晰新信息、具体机制、政策变化或可信研究发现，但无需长篇展开的材料写简讯。简讯应提供机构和日期、具体变化或判断、必要依据及来源，不能只列题名或抽象一句话。可采用已核官方摘要的事实和关键发现，内部如实标注阅读范围，不能冒充全文解读或越过摘要推断。

每周重点解读不少于6篇、简讯不少于10篇，两类分别达标，不能互相抵扣；这是一周期刊的最低数量要求，不是上限，也不是各议题或各国配额。不能将“未达到重点篇门槛”直接当作排除理由。数量不足时，继续复查误排、低分和摘要线索，并在同一七日窗口补查，优先组织模式与制度新做法。不得通过拆分同一报告、重复计数、填充空标题、挪用旧文或恢复用户明确排除项凑数。确实无法达到时保留已完成内容、具体列明缺口与补查结果，标记未达标，不宣称本期完整完成，不静默降低门槛。

## 一、重点文章写成能独立阅读的报告解读

1. 开头自然交代发布机构、日期、作者、报告名称和现实问题，用一段话说明报告在研究什么、主要判断是什么。必要时解释核心概念，不以未经介绍的缩写开篇。
2. 按原报告实际论证组织若干小节。通常可用两至四个有信息量的小标题，但不设固定数量，不强行套“背景—方法—启示”。标题表达具体判断或条件，例如“率先开发模型并不自动形成持久优势”，避免“技术发展与战略赋能”一类抽象标签。
3. 每个主要段落先提出具体判断，再解释依据、案例或机制，并保留足以改变结论的条件。说清谁在什么条件下做什么、为何产生这种结果。数据、案例、比较、情景和制度细节按原文实有内容展开，不要求每段都配数字或案例。
4. 区分作者主张、作者引用的他人观点、假设情景和已有事实。研究人员的实验结果、企业自报、已实施政策及尚未实施的建议不得混写。限定条件直接融入相关论述，不堆积例行免责声明。
5. 首次出现的术语用简明中文解释。保留数字的时期、对象、分母和比较基准；没有可靠数字就用有细节的机制说明，不编数，不把推测写成确定结论。
6. 深度随原报告的实质内容决定。重要报告不能仅压成三五条概括或漫画的扩写；内容简单的材料可作简讯，不拉长凑字数。摘要和漫画从完成的正文提炼；正文保存在 highlights_markdown 或独立“精华选编”，渲染不得截句或删尾。
7. 每篇就报告自身的问题、发现、论证与建议展开。保持多议题选材，不强加企业基础研究、AI4S、区块链、中国或上海关联。保留当前已确认的首页编辑导读和漫画安排。
8. 原文链接和必要来源定位保留。阅读进度、获取记录、核验过程和编选边界进入内部记录；研究对象、时期和实施状态通过具体事实自然交代。

例如，避免只写“先发优势取决于技术扩散和组织能力”。可按用户样例的逻辑展开：报告把先发优势分成能力差距、现实运用和阻断追赶几个环节；军事运用还需要采购、训练与组织调整；模型能力扩散如果快于这些调整，率先发布模型就未必带来持久优势。这里的具体机制比抽象标签更重要。此例来自用户提供的文字，不代替下期原文核读。

## 二、全文获取不能由网页长度代替

- `detail_ok` 仅表示详情请求和提取成功；程序的 `full_text`、字符数、PDF可访问及评分都不是人工精读或覆盖整份报告的证明。
- 对窗口内、有实质研究价值的正式报告，先辨认网页是完整正文、摘要还是导论。出现“Read the full report”“Download PDF”或目录显示网页只含部分章节时，跟进其官方PDF或完整HTML，不能因网页超过5000字符跳过。
- PDF要核对题名、作者、正式发布日期和正文范围，记录具体已核读页段。可以针对选编范围精读，不冒称整份全读。只下载成功或提取出文本不能写成已核读。
- 单个来源失败按原规则跳过并继续其他来源；在逐项记录中写明链接、实际尝试、时间与错误。全文未完成和确实获取失败是两种状态。可用全文尚未核读的有价值报告必须继续处理，不能用“全文待证”作为最终排除理由。
- 付费、限制访问和无法读取的材料不得绕过访问限制。保留明确受阻记录，不把受阻写成无发布，不据摘要编造深读。

## 三、低分不能让正式报告无声消失

- 当期原始复核队列中的全部URL均须有明确去向，补充发现另列并参与同样核验；保留程序原始评分，不靠改分制造收录资格。
- P2/P3、零分及未命中关注词的正式报告同样做题意与公开摘要复核。识别AGI、artificial general intelligence、通用人工智能、superintelligence、超级智能等概念同义表达；它们是复核提示，不是自动升级或硬性收录条件。
- “paper”一词不能自动归为应排除的学术论文。应按发布栏目、用途和实际内容区分智库研究报告、政策简报、学术论文和会议论文。CNAS Reports等正式研究报告须按自身价值判断。
- 对已发现官方PDF且具有实质研究价值的报告，记录全文核读后的取舍理由。简讯数量、来源集中度正常或另一篇同机构评论已收录，都不能代替逐篇判断。

## 四、交付前检查两类遗漏

先对照完整候选队列检查有没有漏掉URL，再检查每条是否停在“待核、待证、导论已读、全文未读”。不能以已浏览标题、审阅行数或文件齐全宣称复核完成。

在当期受版本控制的 `docs/run_receipts/<D>_editorial_review.csv` 中，保留原始列并新增：

| 字段 | 填写规则 |
| --- | --- |
| 最终处置 | 重点、简讯、排除、获取受阻，四选一 |
| 取舍理由 | 具体研究价值或排除依据；不能只写低分、未命中、待证 |
| 全文状态 | 已核读、不需全文、获取受阻、未完成，四选一；正式完成不接受未完成 |
| 正文定位 | 重点与简讯均记录实际采用内容的页码、章节或段落；仅据摘要的简讯准确写摘要定位 |
| 全文获取记录 | 获取受阻时必填，写已尝试的URL、时间、结果；无实际尝试不能填受阻 |
| 写作复核 | 重点与简讯实际对照原文和阅读版后填通过，其余留空 |

重点必须已核读原文；简讯可基于核准的官方摘要且不超出其信息范围。排除可以依据明确无关的题意、材料类型或已核实的窗口外日期，不要求下载所有不相关材料；不得因为尚未读完而排除。取舍仍由实质判断负责，脚本只能检查漏项与未完成状态。

投递前用已验证Python执行本目录 `check_weekly_review.py`，显式传入 `--queue <当期原始_source_health_editorial_review.csv> --review <当期最终复核.csv> --output <当期run_receipts目录下的review_check.json>`。非零退出须先补齐复核再投递。确有证据的单项获取受阻不阻断其他合格材料交付，但须在回执统计。补充候选也写入最终表。原始队列必须非空；零候选周需先在回执核实抓取失败与真实空窗，不能借空表绕过核验。

同时运行本目录 `check_weekly_volume.py --items <当期最终items.json> --review <最终复核.csv> --output <volume_check.json>`，核验至少6篇重点、10篇简讯、独立URL、实质正文及与复核表一致；非零退出先补齐，不按合格周报投递。再逐篇做实质阅读检查：开头是否交代问题，主要段落是否给出具体依据或机制，术语是否解释，引用归属与条件是否准确，全文是否完整渲染。数量和格式检查通过不等于内容质量通过。
