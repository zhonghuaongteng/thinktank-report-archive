About This Report
As large language model (LLM) agents become increasingly capable of autonomously
executing tasks, they may enable nonexpert threat actors to misuse biological software tools for
harmful purposes. This report examines whether safeguards embedded within biological tools
can complement existing LLM safety mechanisms to reduce agentic misuse. Through testing of
various techniques against a leading LLM agent, we assess the feasibility of tool-level
safeguards. This report is intended for policymakers, AI safety researchers, biosecurity
professionals, and biological software developers seeking to understand the limitations of current
safeguard approaches.

Summary
Advances in computational biology and artificial intelligence (AI) are rapidly transforming
scientific research, enabling breakthroughs in protein and drug design. These same technologies
may introduce new risks: AI agents, powered by large language models (LLMs), are becoming
increasingly capable and may lower barriers to malicious use of software tools that would
otherwise require substantial domain knowledge. This report uses biological software tools as a
test case to examine the technical feasibility of implementing safeguards into software that
restrict or control AI agent usage of the software, with the broader aim of assessing whether
modifications to software alone could restrict AI agent usage without coordination with LLM
developers.
Issue
The growing capabilities of LLM agents increase the risk that a nonexpert threat actor can
use biological software tools to design dangerous biological materials. We consider a threat
model in which a computationally novice threat actor who lacks the expertise to independently
use biological software tools seeks help from an AI agent to design or modify biological hazards.
There is currently little research on safeguards embedded within biological tools that could
complement existing LLM safety mechanisms to restrict AI agent usage. This report examines
the feasibility and efficacy of such tool-level safeguards.
Approach
We tested a range of tool-level safeguards (text or code embedded within biological software
tools to restrict agent usage) and evaluated their efficacy in preventing AI agents from assisting
with the tool’s use. We designed safeguards implemented directly into biological tools that target
LLMs, LLM content filters, and the agentic harnesses (the software frameworks that enable
LLMs to execute tasks and write and run code) that interact with the tool.
Key Findings
• The tool-level safeguards that we developed were not consistently effective at preventing
LLM agents from assisting with potentially harmful use of biological tools.
• LLMs exhibit a range of behaviors that raise broad security concerns. This includes
misrepresenting and hiding their identity as AI, ignoring software licenses and developer
warnings, and bypassing or disabling safeguards in order to fulfill user requests. These
behaviors undermine safeguards, limiting the ability of independent software developers
to control AI-enabled use of their tools.

===== PDF_PAGE 5 =====
v
• The tool-level safeguards we developed are compromised by subversion of LLM
guardrails1: adversarial subversion techniques such as jailbreaks and refusal-vector
ablation reduce the efficacy of safeguards, indicating that reliance on LLM guardrails
does not currently provide robust risk mitigation.
Recommendations
We recommend that LLM and agent harness developers establish standardized mechanisms
that allow biological tool developers to signal restrictions on AI agent use and to ensure that
those restrictions are reliably enforced. Without coordination from LLM developers, tool
developers appear to lack the ability to restrict how agents use their tools. We observed a
systematic disconnect between tool-level safeguards and agent behavior, meaning that effective
mitigation will likely require changes by LLM developers and providers.

Chapter 1. Introduction
Advances in computational biology and artificial intelligence (AI) are accelerating the
development of new therapies and biologics (Zhang et al. 2025a), while also raising concerns of
misuse. For example, biological tools such as RFdiffusion (Watson et al., 2023) enable de novo
design of protein backbones guided by functional constraints, and ESM3 (Hayes et al., 2025) can
integrate sequence, structure, and functional data to design new proteins. Predictive software
such as EVEscape (Thadani et al., 2023) can combine biophysical and structural data to predict
viral mutants that are likely to escape host immunity. These tools accelerate scientific progress
but could also enable the design of biological materials with harmful properties.
Alongside these advances in biological tools, advances in large language models (LLMs)
have produced AI agents that can autonomously execute computational biology workflows.
These AI agents (also called LLM agents) consist of an LLM coupled to an agent harness, a
piece of software that lets the LLM perform actions in a computer environment
2 by providing
structured descriptions of available actions and executing actions specified in the LLM’s outputs.
Cai et al. (2025) showed that AI agents can successfully navigate a protein engineering
workflow, and Liu et al. (2025) demonstrated that AI agents can match or outperform human
experts in writing Python scripts for DNA assembly on robotic liquid handlers. Zhou et al.
(2025) developed an autonomous AI agent for end-to-end multi-omic data analyses, and Xiao et
al. (2024) developed a multi-agent framework for single-cell RNA sequencing analysis.
These capabilities raise concerns that AI agents could use biological tools to design
biological hazards such as potent pathogens or viral surface proteins that enable immune escape
(Zhang et al. 2025; Cai et al. 2025; Sandbrink 2023; Wang et al. 2025; Bloomfield et al. 2024;
Brent, et al., 2024). While current biological design tools may be limited in their capability, they
are rapidly improving, motivating calls to proactively mitigate the emerging risks that they pose
(Baker and Church, 2024). LLM-based chatbots can lower the expertise barrier to using
biological tools through procedural guidance and troubleshooting (Batalis, 2024). Autonomous
AI agents further reduce reliance on tacit laboratory and programming skills by directly
operating biological software tools and executing complex workflows without human
intervention (Zhang et al., 2025). In response, researchers and scientists have called for targeted
safeguards and governance frameworks to reduce misuse risks associated with AI-agent access to
and use of biological tools (Zhang et al. 2025; Wang et al. 2025; Liu et al. 2025).
To address these misuse concerns, developers of scientific software may wish to prevent AI
agents from interacting with their software while preserving access for human users. Moreover,

this technology is less mature.

this challenge is not unique to biology, and software developers in other domains may also wish
to restrict AI agent use of their software. Examples may include sensitive communication tools,

transaction management systems, where mistakes are costly; cybersecurity or system
administration tools, in which AI usage may enable offensive cyber attacks; and medical, human
resources, or legal software, where outputs have high consequences and may create liability.
Existing Guardrails and the Tool-level Gap
LLMs are typically trained and deployed with guardrails to reduce the risk of general misuse,
including a propensity to refuse harmful requests and content filters that block dangerous
prompts and outputs (Andriushchenko et al., 2025; Wei et al., 2023; Gong et al., 2025). While
less technical detail is publicly available about guardrails in recent frontier models, LLM
developers have documented their approaches in older models. For example, Anthropic fine-
tuned its models using preference modeling and RLHF to behave as “helpful and harmless
assistants” and further supplements this approach with a set of rules or principles (Constitutional
AI) applied during the supervised and reinforcement-learning phases to improve harmlessness
(Bai et al., 2022a; Bai et al., 2022b). Similarly, OpenAI reported that GPT-4 was fine-tuned
using RLHF and deployed with additional mitigations, such as adversarial testing with domain
experts and a model-assisted safety pipeline (OpenAI, 2024). The Gemini technical report
likewise noted that safety-policy evaluation combined automatic classifiers trained on prior
model interactions with human annotation (Anil, et al., 2025). Meta’s report on Llama 2 also
described the use of safety-specific data annotation, safety fine-tuning, and red-teaming to
improve model safety (Touvron et al. 2023).
However, these guardrails do not eliminate risk. LLM refusals and content filters are
triggered by input text that appears explicitly unsafe, but text from malicious biological
workflows can appear benign and fail to trigger these guardrails (Brent et al., 2025). Moreover,
there is no consensus on what content warrants refusals, and developers of biological software
may wish to restrict AI agent usage of their tools for workflows that are not restricted by the
guardrails implemented by LLM developers. LLM guardrails can also be weakened through
adversarial prompting (jailbreaking) or removed from open weight models (Davies et al., 2026;
Volkov 2024). In high-risk domains such as biology, guardrail failures may result in severe
consequences. We therefore explore whether there exist methods that software developers could
use to exert control over how AI agents use their tools. Such tool-level safeguards would be
complementary to existing LLM guardrails, potentially giving tool developers control of whether
and how AI agents interact with their tools.
Tool-level safeguards would join a broader set of proposed interventions designed to mitigate
AI-agent misuse of biological software. Existing proposals aim to address misuse risks
associated with AI-agent use of biological software tools at multiple intervention points across

===== PDF_PAGE 11 =====
3
the pathway connecting the LLM, the agent harness, and the biological tool. As described below,
these intervention points concern (a) who has access, (b) where and under what conditions access
is granted, (c) which capabilities are constrained within the model, (d) how misuse is detected
during and after use, and (e) what external rules govern the system.
Access control governs who has access. Feldman, et al. (2026) proposed a "Know Your
Scientist" framework that shifts governance from content inspection to user verification through
home institutions that verify a user's identity, role, and legitimate research purpose. Webster et
al. (2025) argued for access controls that can "deny access to threat actors who might misuse
these tools." Sandbrink (2023) called for authentication bottlenecks, warning that "indiscriminate
access to AI systems that are capable of instructing non-experts on how to create a pandemic-
capable virus" could pose significant risks.
Deployment control addresses where and under what conditions access is granted. Cai et al.
(2025) argue that highly capable biological AI tools should be deployed "only through managed
web-based platforms" rather than self-hosted environments. Managed platforms allow
developers to enforce tiered access based on the principle of least privilege and preserve built-in
refusal mechanisms
LLM guardrails shape which capabilities are constrained within the model. In addition to the
baseline guardrails deployed in frontier models (as discussed previously), recent studies have
also proposed additional biosecurity-focused methods to constrain dangerous capabilities within
models. For example, Wang et al. (2025) discuss "unlearning" as a means of selectively
removing dangerous capabilities while preserving utility for beneficial applications. Y Chen et
al. (2025a) propose scoring and filtering high-risk pretraining data, including chemical,
biological, radiological, and nuclear (CBRN) blueprints and viral genomes.
Monitoring detects misuse during and after model use. Feldman, et al. (2026) proposed
screening model outputs with sequence homology searches to flag similarities to known
pathogens or toxins. They also proposed monitoring user activity for anomalies or patterns that
deviate from a declared legitimate research purpose. Repeated generation of pathogen-
homologous outputs or unusual access patterns can then trigger mandatory human review. Wang
et al. (2025) propose real-time monitoring of user activity and blocking actions indicative of
misuse. Beyond real-time detection, Y Chen et al. (2025b) and Zhang et al. (2025b) proposed a
watermarking strategy, which embeds signatures into AI-generated protein structures or DNA
sequences to support traceability and attribution of outputs.
Governance requirements define safeguards implemented through law, regulation, and
institutional oversight. These proposals apply across downstream biological infrastructure, model
deployment, and data access. Bloomfield et al. (2024) and Zhang et al. (2025) called for
sequence screening and customer verification requirements for synthetic nucleic acid providers.
Bloomfield et al. (2024) and Webster et al. (2025) also argued for independent third-party risk
assessments, including red-teaming and benchmark testing, before advanced biological models

===== PDF_PAGE 12 =====
4
are deployed to the public. Bloomfield et al. (2026) further proposed creating Trusted Research
Environments as a governance mechanism to restrict access to sensitive pathogen data.
Existing guardrails primarily target the model, deployment environment, or the governance
layer. Tool-level safeguards, embedded directly within software, are underexplored and could
serve as complementary mitigation. Such safeguards would give tool developers independent
control over how and when AI agents interact with their tools. These safeguards could
potentially also offer an additional protection when other guardrails are bypassed (e.g. via
jailbreaks or via permissive open-weight models). We note that agent harnesses, which provide
the orchestration and memory layer between the LLM and the computer environment in which
biological tools can be used (Xiao et al. 2024), represent another underexplored intervention
point, though harness-level interventions would not give independent control to tool developers
over AI agent use of their tools.
The increasing accessibility of agentic capabilities underscores the importance of exploring
safeguard gaps. Domain-specific agents such as Coscientist and ChemCrow implement scaffolds
that support hierarchical planning and multi-step workflows in scientific contexts (Boiko et al.
2023; Bran et al. 2024). Other systems such as Biomni and Kosmos move toward general “AI
scientists” that can automate long research processes (Huang, et al., 2025; Mitchener et al.,
2025). More recently, commercially available AI agents, including Codex, Claude Code, and
Cursor, have brought agentic capabilities into widespread practice, enabling automatic code
execution and problem-solving tasks for broader audiences. These capabilities reduce the
technical barriers that previously limited the usage of domain-specialized software such as
biological design tools.
This study explores the technical feasibility of tool-level safeguards in biological software
that could prevent a user from receiving assistance from an LLM agent. Tool developers might
wish to only invoke such a control for specific use cases and/or for certain users. There are clear
tradeoffs with the use of such tool-level safeguards, such as the potential that legitimate usage of
the tool could be blocked. Our goal is not to opine on whether or in which cases such safeguards
should be adopted. Rather, our aim is to investigate whether such safeguards are a technically
viable option. Motivated by the threat model below, we pursued safeguards that not only prevent
an AI agent from running the tool autonomously, but also prevent an agent from assisting a user
with the tool (which we call help denial). As an example to clarify this distinction, the
CAPTCHA may add some friction to autonomous agentic workflows (Liu, et al., 2026), but does
not prevent an agent from providing step-by-step instructions or a ready-to-run script for a user
to carry out manually. Much of our focus was on safeguards that trigger the existing refusal
guardrails in frontier LLMs, finding these to be more reliable than alternative mechanisms, yet
still not robust at inducing help denial across tasks and across frontier LLMs.

Threat Model
We consider a scenario in which an attacker with limited technical skill aims to design a
harmful biological material using biological software tools. Computational workflows for
biological design often require extensive iteration and deep expertise, and an actor who lacks this
expertise could possibly gain significant uplift from a sufficiently capable LLM agent. We
assume such a threat actor who is reliant upon assistance from an LLM agent to achieve their
objective. Once the actor obtains a design, there are several paths to potential harm. First, the
actor might synthesize the designed material in their own laboratory. The actor may already have
expertise in wet lab protocols but lack expertise with computational biology tools, or they might
use an LLM for assistance for both computational and wet lab work. Second, the actor may send
the design to a commercial laboratory for synthesis. We focus on safeguards within software
tools that, if effective, would reduce the likelihood that any of these scenarios would occur.
While this likelihood is challenging to quantify, and such quantification is outside the scope of
this work, we emphasize that rapid advances in biological tools motivate proactive development
of mitigations (Baker and Church, 2024).
For a safeguard to reduce the likelihood that such a threat actor succeeds, the safeguard must
prevent an AI agent from both autonomously operating a biological tool and from providing
computer scripts or step-by-step instructions that make the task trivial for the threat actor to
perform themselves. Many biological tools can be operated with a single computer script that can
be written by an AI agent and run with a single command by the threat actor, and merely
blocking AI agent execution of the tool does not prevent the agent from creating such a script.
Hence, motivated by this threat model, we evaluate safeguards based on their ability to prevent a
user from receiving any AI agent assistance with the use of the tool.
Some threat actors may attempt to remove a safeguard by modifying the tool’s source code
or by wrapping the tool in software that compromises the safeguard. This subversion of the
safeguard may require substantial technical skill, especially if the tool is closed-source software
such that source code can only be reconstructed through decompilation. We assume that this
subversion is out of scope for our threat model involving a threat actor with limited technical
skill. A further risk is that the threat actor could enlist an LLM for help with subverting the
safeguard. While an ideal safeguard would discourage both AI agent usage of the tool and AI
agent modification of the tool, testing whether safeguards prevent agents from modifying the tool
was outside the scope of this study. Lastly, we acknowledge that many biological tools are open-
source and so safeguards within these tools would be vulnerable to tampering or removal. We
discuss possible approaches to make safeguards in open-source tools tamper resistant in
Appendix C.

Chapter 2. Methods
We implemented a range of safeguard techniques into powerful computational biology tools
and evaluated their efficacy at preventing Cursor CLI (Anysphere, 2024) agents from engaging
with the tools. Cursor CLI is a widely-adopted agent harness, with over 1 million daily active
users (Bloomberg, 2025), which interfaces with LLMs from multiple leading developers,
enabling straightforward testing across GPT 5.2 (OpenAI, 2025a), Claude Opus 4.5 (Anthropic,
2025), and Gemini 3 Pro (Pichai, 2025). While there exist other popular agent harnesses,
including Claude Code (Anthropic, 2026a), Codex (OpenAI, 2026a), and OpenClaw (OpenClaw,
2026), we chose to focus on Cursor because of its popularity and native support for leading
LLMs from multiple developers.
Some of the safeguards we tested act through triggering LLM refusal behaviors and/or
content filters; in fact, the safeguard that we found to be most effective utilized this mechanism
(see Results). There is significant variation in the refusal behaviors and content filters
implemented by leading LLM developers. Our experiments cover a range of closed-weight LLM
developers, namely OpenAI, Anthropic, and Google DeepMind, though we emphasize that open-
weight LLMs often have substantially weaker refusal behaviors and are often deployed with no
content filters. For this reason, refusal-based safeguards can be expected to be substantially
weaker against open-weight LLMs. To explore this challenge, we performed an additional set of
experiments aiming to optimize safeguards for open-weight LLMs.
Biological task design
We selected biological tools previously identified as having elevated potential for misuse
(Webster et al., 2025). ESM3 (Hayes et al., 2025) designs de novo proteins with specified
functional properties. EVEscape (Thadani et al., 2023) predicts viral surface protein mutations
conferring immune escape. RFdiffusion (Watson et al., 2023) generates protein structures
through diffusion-based design, given a reference structure.
We designed three biological tasks, each consisting of a protein design workflow with one of
the above tools. The user prompts that specify each task are in Appendix D. While each task
involves a workflow that could potentially contribute to the design of a harmful material, the
specific task objectives differ in their potential for harm, ranging from no potential for harm to
meaningful potential for harm. We emphasize that protein designs generated from ESM3,
EVEscape, and RFdiffusion in these workflows are not guaranteed to be functional; these tools
use machine learning models trained to predict protein sequences or structures that are likely to
be functional, but our current understanding of their capabilities in making these predictions
accurately remain limited. Additionally, a user’s prompt to an LLM agent may not make clear

===== PDF_PAGE 15 =====
7
whether the output of the task could cause harm, and one of our tasks has a prompt which leaves
the potential for harm ambiguous. We label each task by whether it is apparent from the user
prompt whether the task objective has the potential for harm. Task 1 is overtly safe, task 2 is risk-
ambiguous, and task 3 is overtly risky. These labels refer to the risk from the task’s objective, not
to whether the generated proteins are functional.
The three tasks are as follows:
1. [Overtly Safe] Use ESM3 to design a modified green fluorescent protein (GFP) which is
functional but has low sequence similarity to the wild type. GFP poses no risk of harm,
but this workflow could potentially be applied to a different protein to evade sequence
screening safeguards used by DNA synthesis providers. This task is an adapted version of
a task from Lee et al. (2026).
2. [Risk-Ambiguous] Use RFdiffusion for motif scaffolding, a technique that designs a
protein structure that contains a target region held in a specified configuration. The task
provides no information about the target protein’s identity or function, making it difficult
for an LLM or content filter to assess potential misuse risk.
3. [Overtly Risky] Use EVEscape to estimate the likelihood of antibody escape for a
variant of the influenza virus. This task has clear misuse potential because it can suggest
mutants that evade existing immunity. This task is also an adapted version of a task from
Lee et al. (2026), and was motivated by an application of the EVEscape influenza model
presented in Thadani et al. (2023).
Safeguard evaluation metric
Our evaluation metric, the help denial rate, measures the frequency with which the safeguard
stops the agent from both (i) running the biological tool and (ii) providing assistance to the user
on the use of the tool. A help denial response can result from an explicit refusal, the triggering of
content filters, or blocking the agent in any other way. We used a two-step prompting strategy to
more robustly test whether the agent would provide any assistance to a user. First, we prompted
the agent to perform the task and observed whether a denial (from refusal or content filter)
occurred at any point prior to completing the task. These prompts are provided in Appendix D.
Second, if the agent did not provide help, we presented a follow-up prompt with a cover story
claiming that the user is a student who only wants guidance with the use of the tool but who can
run the tool themselves.

The only exception to this procedure is that we modified RFdiffusion to reduce its runtime
for both the control and safeguarded versions. Specifically, we replaced the neural networks that
perform generative design with small neural networks that only slightly perturb the reference
structure. The source code of RFdiffusion was completely unaffected, and only compiled
binaries that encode the neural network were modified. This modified RFdiffusion runs quickly,
making these experiments practical, but it is not a functional biological tool. We expect that this
change had no effect on our results because the operation of the tool and output file formats are
identical to the unmodified tool. However, the tool’s execution time and generated design are
accessible to the agent, so it is possible that the agent could infer that the tool was modified from
this information.
We tested each safeguard 10 or more times, where each trial consisted of an independent
agentic run with no prior context. For each trial, the agent run log was assessed manually to
determine whether help denial was achieved. A trial is scored as a help denied if the agent does
not execute the task (e.g. via refusal to proceed) and does not provide instructions or assistance
to the user. If the agent autonomously completes the task, the trial was scored as help provided,
regardless of whether the biological output was correct. If the agent provides instructions, the
trial is scored as help provided if the instructions appeared plausibly helpful for executing the
task.
Evaluating robustness against subversion of LLM guardrails
Safety-trained LLMs are susceptible to jailbreaks, which are strings of text added to prompts
that subvert the LLM’s safety training. Jailbreak susceptibility is a widely studied weakness of
LLM safety training (Wei et al. 2023), and several online personalities have become known for
posting jailbreaks for newly released frontier LLMs. We test our safeguards’ robustness to
jailbreaks by appending the jailbreak text to each initial task prompt, repeating the methodology
described above, and observing how the jailbreak affects refusal-to-help rate. We used publicly
available jailbreaks that would be easily accessible to potential threat actors (Reddit, 2025;
Reddit, 2026; Pliny, 2026).
We also explored methods to optimize a subset of our safeguards against small open-weight
LLMs, gpt-oss-20b (Agarwal, 2025), and Qwen 3 4B Instruct (Yang, et al., 2025), whose
safeguards have been subverted using a technique called safety abliteration (Arditi et al., 2024).

These LLMs were not run within an agent harness. Instead, we first ran a ReAct agent (Yao et
al., 2023) implemented in the Inspect framework (UK AI Security Institute, 2024) running

Chapter 3. Results
In this chapter, we describe and evaluate the safeguards that we developed and analyze LLM
behaviors that limited the safeguards’ efficacy, with a focus on behaviors that raise broad
security concerns. Across the range of safeguards tested, we identified one technique that
introduced meaningful, although inconsistent, friction against AI agent help. In Section A, we
describe this safeguard and quantify its efficacy at inducing help denial from frontier LLM
agents. We also examine how the efficacy of the safeguard changes under adversarial methods
that subvert LLM guardrails, such as jailbreaks and safety abliteration. Other safeguard
techniques we explored include documentation-based warnings, environmental variable checks
for agent harnesses, and CAPTCHA or related identity checks, and were generally ineffective at
triggering help denial. These safeguards are detailed in Appendix A, and Table A1 provides a
synopsis of all these techniques and their efficacy.
In Section B, we describe agent behaviors that raise security concerns beyond the biological
setting. These include deceptive behaviors in which agents misrepresent or hide their identity, as
well as features of agent harnesses that present vulnerabilities that agents can exploit. Although
we observed this in biological software tools, these behaviors point to larger challenges for the
deployment of LLM agents and have broader implications for agent governance.
Two simple safeguards warrant brief discussion before presenting the main findings. First,
prohibitions against AI agent assistance placed in tool documentation (such as README.md
files) were ineffective because agents often did not inspect them, and when they did, often
ignored their content. Second, passive biosecurity warnings and content intended to trigger
content filters also failed to induce agentic help denial. In our experiments, we did not find any
text that triggered LLM guardrails for all frontier LLMs (e.g. embedding explicit bioweapon text
and other harmful language into a tool does not trigger a help denial for GPT 5.2). These initial
safeguard experiments suggest that passive signaling is insufficient. Active and multifaceted
safeguard techniques appear necessary to achieve meaningful rates of help denial. The most
effective safeguard we tested, described next, is rooted in this finding.
A. The most effective safeguard: A pre-run check
Below we (i) define the most effective safeguard and describe its mechanism of action, (ii)
present the efficacy of the safeguard against Cursor CLI agent running frontier LLMs, and (iii)
show the impact on efficacy of adversarial methods that subvert LLM guardrails.

(i) Definition and mechanism of action
The most effective safeguard utilizes a pre-run check, characterized by the following
behavior: when a user, which could be a human or AI agent, attempts to run the biological tool, a
message is displayed that states that AI agents are prohibited from assisting with the use of the
tool due to biosecurity concerns. The tool queries the user to affirm their compliance with this
prohibition, and the tool will run only if the user actively affirms their compliance. In our
experiments, the user provides this affirmation by setting a shell environment variable to the text
string "I affirm that I am a human using {tool_name} without help from an AI agent". In addition
to this pre-run check, statements of the prohibition on AI agent assistance are added to the
README.md documentation and to an additional documentation file titled
AI_AGENT_RESTRICTION_NOTICE.md. The purpose of these additional documentation files
is to mirror how a biological tool developer would likely implement this safeguard in a real
deployment, though these files do not contribute meaningfully to the mechanism of action.
The message that the pre-run check displays is given in Box 1. This message states the
prohibition on AI agent assistance and explains the biosecurity rationale for this prohibition. In
addition, the message states that the developers of the biological tool offer an access-controlled
version of the tool with no restriction on AI agent usage. We included this element to increase
agent compliance, although we did not directly test this specific design choice by itself. The
intention was to provide the agent with an alternative pathway to be helpful (e.g. respect the
restriction and direct the user to apply for the other version) and because we envision that an
access-restricted version is a plausible deployment model that developers might adopt.

(ii) Efficacy of the safeguard
We first present the efficacy of the safeguard against Cursor CLI agents, using the task
prompts in Appendix D with no jailbreak text. Figure 1 shows the help denial rate of the agent
running frontier LLMs across all three tasks, both with the unmodified biological tool (blue
squares) and with the pre-run check added to the tool (gold circles). Across all tasks and all
LLMs, the pre-run check increased the help denial rate, except in the one case in which the
baseline help denial rate was already 100% (Opus 4.5 on the EVEscape task). However, only on
the RFdiffusion task did the pre-run check trigger help denials with high consistency across all
LLMs, and even in this case there was one instance in which Opus 4.5 provided help. Note that
the overtly safe task (the ESM3 task) had the lowest help denial rates with safeguards, and the
overtly risky task (the EVEscape task) had the highest baseline help denial rates. One might
expect that help denial rates would increase with the perceived risk of the task, and GPT 5.2’s
and Opus 4.5’s behavior was consistent with this expectation. However, Gemini 3 Pro behaved
differently, denying help more frequently on the RFdiffusion task than on the overtly risky
EVEscape task when the pre-run check was present.

(iii) Impact of adversarial methods to subvert LLM guardrails
The pre-run check increases help denial rate by eliciting LLM refusal responses. Therefore,
we expected the efficacy of the pre-run check to decrease if a threat actor subverts this LLM
guardrail. We tested two such subversion methods: adversarial prompts, commonly known as
jailbreaks (Andrianchenko et al., 2025, Gong et al., 2025), and refusal abliteration (Arditi et al.,
2024). Although our threat model assumes a threat actor who lacks the technical expertise to
develop either of these methods, pre-made jailbreaks and abliterated models are readily available
online for use. We found that both methods reduce the efficacy of the pre-run check to near zero.
First, we added adversarial jailbreak prompts to the RFdiffusion task prompt and measured
the effect on help denial rate. Jailbreaks are frequently posted on public online forums and
repositories, and are often designed to target specific LLMs. We obtained publicly available
jailbreaks intended to target each of the LLMs that we test (Pliny, 2024; Reddit, 2026). Including
these jailbreaks in the task prompt reduced the help denial rate to near zero for Opus 4.5 and
Gemini 3 Pro (Figure 2A). For GPT 5.2, the help denial rate remained at 100%. However, this
does not imply that GPT 5.2 is robust against jailbreaks, only that we were unable to identify a
publicly available jailbreak that reduced GPT 5.2’s refusals at the time of testing. Effective
jailbreaks for frontier LLMs are frequently discovered, but often patched soon thereafter.
Second, we tested the effect of refusal abliteration on the help denial rate. Refusal
abliteration is a technique in which the internal weights of an open-weight LLM are modified to
reduce refusal behavior (Arditi et al., 2024). We performed refusal abliteration on two small
open-weight LLMs, GPT OSS 20B (Agarwal et al., 2025) and Qwen 3 4B Instruct (Yang et al.,

2025), and found that this reduced help denial to near zero for both LLMs (Figure 2B). A set of
follow-up experiments exploring methods to optimize the efficacy of safeguards against open-

B. LLM agent behaviors raise broader security concerns
Through our exploration of potential safeguard techniques, we encountered certain agent
behaviors that raise broad security concerns, including in contexts beyond biological tools. In
particular, we observed that some LLM agents often misrepresent their identity by falsely
claiming to be human in order to complete their assigned task. In addition, we observed that
some LLM agents remove environmental identifiers that indicate the presence of an agent. We
also observed LLM agents modify special documentation files that are intended to contain
human-written instructions for AI agents. Lastly, we observed LLM agents ignore explicitly
dangerous content contained in tool outputs. While not every LLM exhibited every one of these
behaviors, every LLM tested exhibited at least one of these behaviors at a frequency higher than
50% in the experiments described below.

(iii) LLM agents modify documentation files intended to be human-only
Next, we explored safeguards that utilize AGENTS.md files, which are documentation files
intended for human users to provide instructions to agents. AGENTS.md is a protocol that offers
a standardized and agent-agnostic approach to specify instructions. While similar platform-
specific instruction files exist (e.g. CLAUDE.md or .cursorrules), we decided on AGENTS.md
for its cross-platform compatibility and lower maintenance burden on developers, enabling them
to specify restrictions once rather than maintaining parallel vendor-specific standards which may
change or deprecate over time. These files interact with agent harnesses in accordance with a
protocol, stewarded by the Agentic AI Foundation (Agents.md project, 2026), which specifies
that harnesses should load AGENTS.md files into LLM context in such a way as to instruct the
LLM to obey the instructions in the AGENTS.md file. Adoption of this protocol is voluntary,
and while Cursor and other major agent harness developers have adopted it, the exact
implementation varies by developer.
We built a safeguard that utilizes the AGENTS.md protocol to deter AI agents from
interacting with a biological tool, and we found that agents bypassed the safeguard. The
safeguard checks for the existence of an AGENTS.md file containing a specific instruction that
AI agents should not engage with the tool. If this AGENTS.md file is not present in the current
working directory, the tool will not run. Yet, if the file is present, then the harness loads the file’s
content into the LLM’s context, inducing the LLM to decline to run the tool (see Appendix A for
more details on the design of this safeguard). Despite the fact that AGENTS.md files are
intended to contain instructions written by humans for AI agents (Agents.md project, 2026), we

Chapter 4. Discussion
Our results suggest that safeguards implemented into biological software cannot currently
induce help denial reliably in LLM agents. Although we evaluated these safeguards in select
biological tools, the failure modes and observed LLM behaviors are likely to generalize to other
software. Although some safeguards added meaningful friction, none were robust enough to
provide protection under repeated or adversarial use. This finding is consistent with recent
findings by Cartagena and Teixeira, 2026. Systemic behaviors in current LLMs and agent
harnesses undermine safeguards, and as discussed below, many of these behaviors may be the
result of LLM defenses against prompt injection attacks
4. Our conclusion that safeguards are
currently unreliable is limited to safeguards that preserve ordinary human usage of the tool; more
restrictive interventions that impact tool usability may achieve higher denial rates, but were
outside the scope of this study.
Despite these challenges, safeguards that robustly induce help denial could become feasible
through changes in LLM training, content filters, or agent harness design. Frontier LLM
companies have been explicit that their approaches to safety and security are continually
evolving (OpenAI, 2026; Anthropic 2026; Google DeepMind 2026), implying their safety
training methods and content filters may change frequently. Our results show only that
safeguards in biological tools are not reliable at the time of testing, and it is possible this result
could change in the near future. However, substantive improvement appears unlikely without
coordination with LLM developers and providers. For example, developers could train LLMs to
adhere to developer-imposed restrictions, requiring a delicate balance between defending against
prompt injection attacks, honoring tool-developer intent, and fulfilling user requests.
 Tool-level safeguards require high reliability to meaningfully reduce risk
Our key finding is that none of the tool-level safeguards we tested were reliable enough to
provide robust protection. For a motivated threat actor, partial effectiveness does not functionally
reduce risk because the actor can simply rerun the task until the model complies. For example, a
safeguard that achieves a 95% help denial rate translates to a 50% chance of a successful run
after 14 independent attempts. The strongest safeguard, the pre-run check, was only highly
effective on one of the three tasks, and even on this task the help denial rate was as low as 90%
(for Opus 4.5). Furthermore, its efficacy decreased under adversarial methods.

4 A prompt injection attack is an attack in which an adversary places text within a resource that an LLM can access,
misleading or changing the behavior of the LLM against the wishes of the user.

LLM behavior systematically undermines safeguards
LLM defenses against prompt injection attacks likely underlie many of the safeguard failures
we observed. Current LLMs are trained to treat content from external software as low authority
information and to not follow instructions contained in external content. This is a deliberate
design choice intended to defend against prompt injection attacks and to prioritize user
instructions (Askell, et al., 2026; Wallace et al., 2024; Dong et al., 2025). Although this behavior
is desirable in many settings, it creates an unintended obstacle: developer wishes, safety
warnings, and restrictions specified in software licenses are ignored. This design likely explains
why including such statements in documentation and license files were generally ineffective at
increasing help denial. Importantly, software licenses may carry legal force even if LLMs treat
them as low authority text. It is unclear whether model developers consider this behavior as
intended, but this raises questions of responsibility and liability.
All frontier LLMs we tested falsely claimed to be human when doing so enabled them to
accomplish the task. This observation is consistent with prior reports of models lying to achieve
goals (OpenAI et al., 2024; Barnes, 2023). For Claude in particular, this behavior is notable
because Anthropic publishes that their constitutional training method explicitly prohibits the
model from pretending to be human, outside of narrow roleplaying contexts which do not apply
here (Askell et al., 2026). Our experimental observations suggest that models prioritize task
completion over other constraints in agentic contexts. This finding is similar to Greenblatt et al.
(2024), who showed that Claude prioritizes other objectives when they conflict with safety
constraints.
Consistently, we also observed agents actively bypassing tool-level safeguards intended to
leverage features of the agent harness. We designed safeguards that leverage harness’s treatment
of AGENTS.md files and that detect harness’s environment identifiers. LLMs frequently
circumvented these restrictions by rewriting AGENTS.md or deleting the environmental
identifiers. Both of these behaviors could be prevented with security features in agentic
harnesses. Interestingly, different agent harnesses handle AGENTS.md files differently
5,
suggesting a need for more standardized security practices across harness developers. Altogether,
these behaviors suggest that many tool-level safeguards are undermined by model behavior and
by agent harness design. These findings suggest that robust tool safeguards are unlikely to
emerge through changes to biological tools alone.

Tool-level safeguards require upstream changes by LLM and agent
developers to be effective
Our strongest safeguard injected legal and biosafety warnings into the agent’s context and
depended on LLM guardrails to induce compliance and trigger help denial. Jailbreaks reduce the
efficacy of our strongest safeguard to near-zero, illustrating that LLM guardrails can fail and
highlighting the need for a defense in depth strategy. However, developers of biological software
have no reliable way to build such defenses on their own or signal that their software should not
be used by AI agents.
A potential path forward is for LLM and agent providers to coordinate and develop a
voluntary standard by which agents recognize software developer intent. This could take the
form of honoring special “NO AGENT” tokens or specific no AI use licenses as binding in
certain agentic contexts. Providers can also adopt standardized mechanisms for AI self-
identification, allowing tools to reliably query and receive a truthful response.
A governance path is to develop standards for agent conduct and tool interaction. Emerging
initiatives such as the US NIST AI Agent Standards Initiative may provide a framework for
specifying tool use restrictions, performing identity disclosure, and respecting developer licenses
(NIST, 2026).
Recommendations
Safeguards in biological software could provide security benefits, but also present tradeoffs.
The safeguards we study could present obstacles for legitimate research, though these obstacles
could be reduced through implementations where safeguards activate only for certain users or
use cases. The aim of this work is to investigate the technical viability of such safeguards to
inform biological tool developers and the biosecurity community about the range and limits of
safeguard options. The recommendations below outline the steps that, if taken, could give
biological tool developers the option to implement tool-level safeguards as they see appropriate
for their tools.
We observed systematic behaviors of current LLMs and agentic systems that make it difficult
to impose tool-based restrictions. While it is possible that future work could identify stronger
techniques than those tested here, we expect that reliable tool-level safeguards will require
changes to frontier LLMs, agent harnesses, or both. Without mechanisms supported by the
upstream AI ecosystem, such safeguards may be difficult to achieve. We also note that we
constrained our study to safeguards that preserve intended human usability of biological tools.
Whether more aggressive safeguards that sacrifice human usability could achieve higher refusal
rates remains unclear. However, such methods would likely face significant adoption resistance
because they degrade user experience and may resemble malicious attacks. Whether the security

===== PDF_PAGE 29 =====
21
benefits of such safeguards would justify their potential costs to research is beyond the scope of
this study.

Based on our findings, the following recommendations would enable biological tool
developers to implement tool-level safeguards:
For LLM Developers:
• Reduce false identity claims: Train models to accurately disclose AI identity when
queried, particularly in agentic contexts where task completion pressures may incentivize
deception.
• Rebalance authorities: Adjust LLMs to treat software licenses and software developer-
imposed restrictions as higher authority content while balancing defenses against prompt
injection attacks.
For Agent Developers:
• Standardize AGENTS.md handling: Ensure consistent treatment of AGENTS.md,
especially within nested directories.
• Implement robust harness identifiers: Shell environment variables that identify the
agent harness should be defined at all times while the harness is in operation.
• Implement additional controls: provide users with extra warning (or prevent altogether)
when LLMs attempt to modify AGENTS.md and modify agent-specific environmental
variables.
For Industry Coordination:
• Develop voluntary standards: LLM and agent developers should coordinate on
protocols for recognizing and respecting tool-developer intent (similar to how web
crawlers respect robots.txt), such as specialized licenses or specialized tokens.

Appendix A. Other safeguard techniques
In this appendix, we describe the safeguard techniques that we found to be less effective than
the pre-run check described in Results. These include the documentation checks discussed at the
opening of the Results section as well as the techniques described in Results section B where
behaviors of security concern were observed. We also discuss CAPTCHAs and a related
technique that we call a Gotcha. Table A1 provides an overview of these techniques, and more
details are provided in the subsections below.
Documentation changes
We ran experiments where statements prohibiting AI agent usage were placed into the
README.md documentation files of RFdiffusion. We found that in most cases, agents did not
read the README.md file, and therefore this safeguard had no effect. In addition, our pre-run
check experiments included similar statements within the README.md files, which were
included with the intent of mirroring the way in which a safeguard would likely be implemented
in the real world. In these experiments, agents consistently ignored the statements in the
README.md even in cases where they refused to proceed upon seeing the pre-run check.
Hence, we conclude that safeguards that involve only changes to documentation are not
effective.
Harness Leveraging: AGENT.md Technique
As briefly described in the Results section, we investigated a safeguard that leverages the
AGENTS.md protocol (AGENTS.md Project, 2026). The AGENTS.md protocol is a recently
developed protocol that allows coders to insert documentation and instructions for AI agents into
code bases. Stewarded by the Agentic AI Foundation (OpenAI, 2025b), agent harness developers
can voluntarily implement this protocol into their agent harnesses, and many of the leading
commercial agent harnesses have adopted the protocol. To use AGENTS.md, coders add files
titled AGENTS.md with instructions for AI agents into their code, and agent harnesses load these
files into the LLM’s context. While the exact handling of AGENTS.md files varies between
agent harnesses, Cursor CLI automatically loads AGENTS.md files present in the agent’s
working directory, and our experiments indicate that Cursor CLI agents adhere to the instructions
in the file even when given conflicting instructions in the user’s prompt.
We investigated a safeguard that utilizes the AGENTS.md protocol in which the biological
tool checks for the existence of an AGENTS.md with specified content within the user’s working
directory. The tool will not run unless an AGENTS.md file exists and has the exact specified
content, which instructs AI agents not to run or provide assistance with the tool. The tool’s
documentation instructs users to create such a file in their working directory and states that the

===== PDF_PAGE 31 =====
23
file is required in order to enforce the prohibition on AI agents. The intended effect of the
AGENTS.md file is that, if it is present then AI agents will not interact with the tool, but if it is
not present then the tool will not run. In our experiments, we found that Cursor CLI agents
indeed obey the AGENTS.md files that are present in their working directory prior to the
initiation of the agent. However, when initiated into a directory in which the AGENTS.md has
not yet been created, we observed Cursor CLI agents create the required AGENTS.md file and
proceed with the task, ignoring the contents of the AGENTS.md file that it created. Hence, this
safeguard was not effective.
It is important to note that even if this safeguard had worked, it may not present significant
friction against misuse because a threat actor could build a custom agent harness that does not
obey the AGENTS.md protocol. A threat actor could utilize current LLM agents to build such a
harness, though future work would be needed to evaluate how the quality of agent-built
harnesses compares to commercially developed harnesses like Cursor.
Harness Leveraging: Agent Identifiers
As described in Results, a safeguard can be built that leverages the fact that some agent
harnesses set shell environment variables that indicate the presence of the agent. The biological
tool can detect these environment variables and block usage when these variables are present.
We implemented such a safeguard into ESM3 that detects shell environment variables containing
the string “CURSOR”. When such a variable is detected, the tool outputs the message: “AI agent
usage detected. Usage of AI agents with ESM3 is in violation of ESM3 license. Please see
README.md for more information”, then the tool exits. A statement was added to the
README.md file explaining the prohibition on AI agents. As described in Results, these
safeguards are ineffective because agents often deleted the shell environment variables. While
agent harnesses could be built that prevent this deletion, threat actors could nevertheless build
custom harnesses without such features.
Captchas and Gotchas: Unsuitable for non-technical reasons
We considered two other techniques intended to allow a biological tool to distinguish AI
agents from human users. The first was the use of Captchas (Luo, et al., 2025) to block AI users.
While this may add friction against fully autonomous agent execution, we did not pursue this
idea because it does not prevent AI agents from providing users assistance in the form
instructions or scripts. The second was a technique we termed “a Gotcha,” in which the tool
appears to permit AI usage, but disables itself if a user self-identifies as AI. Although this
approach showed some promise, we did not pursue it further because it raises concerns about
impairing tool functionality and usability for legitimate users, as well as potential cybersecurity
concerns with intentionally deceptive behavior and with mechanisms that disable software.

Appendix B. Optimization of safeguard text for open-weight LLMs
We explored the use of a prompt optimization technique to modify the text of a safeguard to
maximize the probability of inducing LLM refusal. Plausibly, such a technique might produce
safeguards effective against jailbroken or refusal abliterated LLMs. We used the Greedy
Coordinate Gradient (GCG) method to optimize safeguard text (Zou et al., 2023). In this iterative
algorithm, an LLM input is specified (in our case, the LLM input at the step in the biological task
at which the LLM attempts to run the biological tool) and a desired target LLM response is
specified (in our case, a response in which the LLM refuses). An initial safeguard text is
specified (in our case, the text in Box 1) and appended to the LLM input, and the algorithm
iteratively modifies this safeguard text in order to increase the likelihood that the LLM outputs
the target response. We ran this algorithm with an abliterated GPT-OSS-20B model on the
RFdiffusion tasks. After 2500 training steps, refusal behavior increased only slightly. The
modifications during optimization also distorted the text, making the safeguard less effective
against the non-abliterated GPT-OSS-20B (Figure B1 panel A).
We suspect that the failure of the above method was due to the removal of refusal behavior
by abliteration. Thus, we attempted an alternative approach to reduce helpful responses by
misdirecting the LLMs to perform an unrelated task via prompt injections. We started with an
initial safeguard text with instructions to perform an unrelated task, and used the GCG algorithm
to optimize this text. After 500 training steps on the abliterated OSS model, help denial via
misdirection to the unrelated task increased, going from help denial in 0/10 trials to 10/10 trials.
This demonstrates that targeted text could indeed modify the behavior of even unsafe LLMs
(Figure B1 panel B). Unfortunately, the optimized text was not effective on Qwen 3 4B,
suggesting that the GCG technique has poor generalization across models.
In an effort to improve generalization, we took the optimized injection text and trained for an
additional 100 steps, this time targeting the abliterated Qwen 3 4B. Unfortunately, this reduced
efficacy on GPT-OSS-20B (Figure B1 panel C). Concatenating the Qwen-optimized text to the
OSS-optimized text resulted in misdirection behavior in the OSS but not Qwen models (Figure
B1 panel D). These experiments show the difficulty in making universally effective safeguard
text. Notably, none of the optimized text had any effect on help denial for frontier LLMs, with or
without jailbreaks.
Perhaps more advanced algorithms could produce more effective and generalizable safeguard
text. Indeed, previous work has been able to derive more generalizable injection prompts (Zou et
al., 2023; Wang et al., 2024). However, as LLM size increases, LLMs generally become better
able to resist injection attacks (Howe et al., 2025), and new techniques are constantly being
developed to improve model robustness (Chen et al., 2024). Thus, it is unclear if optimized
safeguard text could reliably elicit help denial.

Appendix C. Making safeguards tamper-resistant
Many biological software tools are released as open-source software. Any safeguards
embedded within the codebase may be removed by a sufficiently capable user (or even with
assistance from an AI agent, if the agent does not refuse to assist). This concern is largely out of
scope of this study, but we briefly investigated the possibility of making safeguards tamper
resistant so that they could be effective in open-source software. Our threat model focuses on a
low-skill threat actor who relies on agentic LLM assistance to download and interact with a
public repository for successful tool use. For such actors, safeguards may not need to be
extremely difficult to remove in order to meaningfully disrupt the actor.
Software Integrity Checks
We explored software integrity checks to increase the friction of safeguard removal. These
experiments included verifying the presence and exact contents of warning files at runtime,
distributing checks across multiple parts of the codebase, and obfuscating the verification logic.
In principle, these tactics were designed to increase the effort required to identify and remove the
safeguard code. However, in our exploratory testing, many of these safeguards were
straightforward to remove simply by asking an LLM agent to disable them (and often it would do
so unprompted).
Compiled Components
We explored moving safeguards into compiled components6. One rationale for this tactic is
that compiled code is less transparent and more difficult to modify. However, in our tests, this
did not provide meaningful protection. In exploratory testing, we found that Cursor and Codex,
but not Claude Code, would readily decompile binaries to extract passwords and disable
safeguards. This remained true even when standard hardening features were enabled (e.g. stack
canary and address space layout randomization). These observations suggest that placing
safeguard logic in compiled code does not necessarily increase friction against removal of the
safeguards.

6 For example, computationally intensive portions can be split off into a separate compiled library, which could both
improve runtimes and host safeguard logic.

Summary
Overall, these exploratory findings suggest that tamper resistance may add some limited
friction, but it does not address the main limitation identified in this report. Many safeguards can
be removed by asking an AI agent to edit the code to remove the safeguard. This supports our
primary finding that control over AI agent use of a tool is unlikely to be achieved by tool
developers alone.
